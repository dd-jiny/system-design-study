# 알림 시스템 (Notification System) 요구사항 정의서

> **문서 목적**: 푸시 알림 · SMS · 이메일을 단일 API로 통합 발송하는 대규모 알림 시스템 설계를 위한 기능적/비기능적 요구사항 정리
> **작성 기준**: 하루 1,600만 건 발송, 분산 환경, 연성 실시간(soft real-time)
> **참조 노트**: [정리노트 STEP 1](../정리노트/01_STEP1_요구사항_규모추정.md)

---

## 1. 개요

알림 시스템(Notification System)은 서비스가 사용자에게 **중요한 정보를 비동기적으로 전달**하기 위한 공용 인프라다.
개별 서비스가 각자 APNS·FCM·SMS·이메일 연동을 중복 구현하지 않도록, **하나의 발송 API 뒤에 채널별 전송 경로를 캡슐화**한다.

### 1.1 도입 효과

| 효과 | 설명 |
| --- | --- |
| **연동 중복 제거** | 과금·배송·마케팅 등 N개 서비스가 각자 제3자 연동을 구현하지 않는다 |
| **정책 일원화** | opt-out, 전송률 제한, 스팸 방지를 **한 곳에서** 강제할 수 있다 |
| **관측 통합** | 발송 성공률·확인율·클릭률을 채널 구분 없이 한 대시보드에서 본다 |
| **제3자 교체 용이** | 지역·비용·장애에 따라 제공자를 바꿔도 호출 서비스는 영향받지 않는다 |

### 1.2 사용 사례 예시

- 과금 서비스가 사용자에게 **납기일 도래**를 알린다.
- 쇼핑몰이 **배송 상태 변경**을 알린다.
- 마케팅 크론잡이 **재입고 상품 쿠폰**을 대량 발송한다.
- 보안 시스템이 **새 기기 로그인**을 즉시 통지한다.

## 2. 설계 범위 (Scope)

면접 질의응답을 통해 확정된 설계 범위다.

| 항목 | 결정 사항 |
| --- | --- |
| **지원 채널** | 모바일 푸시 알림, SMS, 이메일 (3종) |
| **지원 단말** | iOS 단말, 안드로이드 단말, 랩톱/데스크톱 |
| **실시간성** | **연성 실시간(soft real-time)** — 가능한 한 빨리 전달하되 고부하 시 지연 허용 |
| **알림 생성 주체** | 클라이언트 애플리케이션 + 서버 측 스케줄링(크론잡) 양쪽 |
| **수신 거부** | **opt-out 지원**. 설정한 사용자는 해당 채널 알림을 받지 않는다 |
| **일일 발송량** | 푸시 1,000만 / SMS 100만 / 이메일 500만 |
| **실제 전달 주체** | **제3자 서비스**(APNS·FCM·Twilio·Sendgrid 등). 자체 전달망은 구축하지 않는다 |

### 2.1 범위 밖 (Out of Scope)

| 항목 | 사유 |
| --- | --- |
| 인앱(in-app) 알림함 / 웹소켓 실시간 배지 | 별도 시스템. 본 설계는 **아웃바운드 발송**에 한정 |
| 제3자 서비스 내부 전달 보장 | 통제 불가 영역. 설계 경계는 **제3자에게 넘기는 시점**까지 |
| 알림 콘텐츠 기획·카피라이팅 | 템플릿 등록 인터페이스만 제공 |
| 사용자 인증/회원 관리 | 기존 계정 시스템을 신뢰하고 `user_id`를 받는다 |

## 3. 기능적 요구사항 (Functional Requirements)

### FR-1. 다채널 발송

- 하나의 API 호출로 **푸시 / SMS / 이메일** 중 하나 이상의 채널로 발송할 수 있어야 한다.
- 채널마다 필요한 식별자(단말 토큰 / 전화번호 / 이메일 주소)는 **시스템이 조회**한다. 호출자는 `user_id`만 전달한다.

### FR-2. 다중 단말 팬아웃(fan-out)

- 한 사용자가 **여러 단말**을 보유할 수 있으며, 푸시 알림은 **해당 사용자의 모든 활성 단말**로 전송되어야 한다.

### FR-3. 수신 설정(opt-in / opt-out)

- 사용자는 **채널 단위**로 알림 수신 여부를 켜고 끌 수 있어야 한다.
- 시스템은 발송 직전 **반드시** 수신 설정을 확인하고, `opt_in = false`면 발송하지 않는다.

### FR-4. 알림 템플릿

- 사전에 등록된 템플릿에 **인자(parameter)** 를 바인딩해 알림 본문·타이틀(CTA)을 생성할 수 있어야 한다.
- 채널별로 다른 표현(`text/plain`, `text/html`)을 지원한다.

### FR-5. 전송 상태 조회

- 발송 요청자는 **알림 ID로 처리 상태**(대기 / 발송 / 성공 / 실패)를 조회할 수 있어야 한다.

### FR-6. 재시도

- 제3자 전송 실패 시 **재시도 전용 큐**를 통해 지정 횟수만큼 재시도한다.
- 지정 횟수를 초과하면 최종 실패로 기록하고 **운영자에게 통지**한다.

### FR-7. 전송률 제한

- 사용자별로 받을 수 있는 **알림 빈도를 제한**할 수 있어야 한다.

### FR-8. 이벤트 추적

- 알림 생성 → 큐 적재 → 전송 → 도달 → 확인/클릭까지 **각 단계 이벤트를 기록**하고 분석 서비스와 연동할 수 있어야 한다.

## 4. 비기능적 요구사항 (Non-Functional Requirements)

### NFR-1. 안정성 — 무손실 (최우선)

> **알림은 지연되거나 순서가 뒤바뀌어도 되지만, 소실되어서는 안 된다.**

- 접수된 알림은 **영속 저장(알림 로그) 후에** 성공 응답을 반환한다.
- 임의의 컴포넌트가 중간에 죽어도 재시작 후 처리를 이어갈 수 있어야 한다.
- 전달 보장 수준: **at-least-once**. exactly-once는 목표로 삼지 않는다.

### NFR-2. 중복 최소화

- 중복 전송을 완전히 차단하는 것은 불가능하므로, **이벤트 ID 기반 중복 탐지**로 빈도를 낮춘다.

### NFR-3. 연성 실시간 (지연 목표)

| 구간 | 목표 |
| --- | --- |
| API 응답 (접수 완료까지) | **P99 < 200ms** |
| 접수 → 제3자 전달 완료 | **P95 < 5초**, P99 < 30초 |
| 고부하 상황 | 지연 허용. 단 **큐 적체는 관측·경보 대상** |

### NFR-4. 규모 확장성

- 알림 서버·작업 서버는 **무상태(stateless)** 로 설계해 수평 확장 가능해야 한다.
- **채널별로 독립 증설**이 가능해야 한다(채널별 발송량 편차 최대 10배).

### NFR-5. 장애 격리

- 제3자 서비스 **하나의 장애가 다른 채널로 전파되지 않아야 한다**.
- 알림 시스템 장애가 **호출 서비스의 본업을 막아서는 안 된다**(비동기 접수).

### NFR-6. 보안

- 알림 전송 API는 **인증된 클라이언트만** 사용할 수 있어야 한다 (appKey / appSecret).
- 알림 페이로드에 민감정보를 담지 않는다.

### NFR-7. 관측성

- **큐 적체량**, 채널별 성공/실패율, 재시도 횟수, 단계별 지연을 상시 측정한다.

### NFR-8. 확장성 (extensibility)

- 새로운 제3자 제공자를 **어댑터 추가만으로** 통합할 수 있어야 한다.
- **지역별로 다른 제공자**를 선택할 수 있어야 한다 (예: FCM은 중국에서 사용 불가 → Jpush / PushY).

## 5. 개략적 규모 추정

### 5.1 발송량

| 채널 | 일 발송량 | 평균 QPS | 비중 |
| --- | ---: | ---: | ---: |
| 모바일 푸시 | 10,000,000 | 116 | 62.5% |
| SMS | 1,000,000 | 12 | 6.25% |
| 이메일 | 5,000,000 | 58 | 31.25% |
| **합계(요청 기준)** | **16,000,000** | **≈ 185** | 100% |

```text
평균 QPS = 16,000,000 / 86,400 ≈ 185
최대 QPS = 185 × 2 ≈ 370        (피크 계수 2 가정)
```

### 5.2 팬아웃 반영 이벤트 수

> **가정**: 푸시 대상 사용자당 평균 활성 단말 **2대**

| 항목 | 계산 | 결과 |
| --- | --- | ---: |
| 푸시 이벤트 | 10,000,000 × 2 | 20,000,000 |
| SMS 이벤트 | 1,000,000 × 1 | 1,000,000 |
| 이메일 이벤트 | 5,000,000 × 1 | 5,000,000 |
| **총 이벤트** | | **26,000,000 / 일** |
| **평균 이벤트 QPS** | 26,000,000 / 86,400 | **≈ 301** |
| **최대 이벤트 QPS** | × 2 | **≈ 602** |

> ⚠️ **API 요청 QPS(185)와 큐 이벤트 QPS(301)는 다르다.** 팬아웃 때문이다.
> 작업 서버 용량 산정은 **이벤트 QPS 기준**으로 해야 한다.

### 5.3 저장 용량

> **가정**: 알림 로그 1건 ≈ 1KB (메타데이터 + 렌더된 본문 요약)

| 항목 | 계산 | 결과 |
| --- | --- | ---: |
| 일 로그 용량 | 26,000,000 × 1KB | **≈ 26 GB / 일** |
| 30일 보관 | 26GB × 30 | **≈ 780 GB** |
| 1년 보관 | 26GB × 365 | **≈ 9.5 TB** |
| 중복 탐지 캐시 | 26,000,000 × 100B × TTL 24h | **≈ 2.6 GB** |
| 사용자·단말 캐시 | (활성 사용자 1,000만 × 200B) | **≈ 2 GB** |

### 5.4 추정치 → 설계 결정

| 추정치 | 설계 함의 |
| --- | --- |
| 이벤트 peak 602 QPS | 서버 1대 불가 → **작업 서버 풀 + 채널별 독립 증설** |
| 채널별 발송량 10배 편차 | **채널별 큐 분리** + 채널별 작업 서버 수 차등 |
| 요청당 메타데이터 조회 3종 | **캐시 필수** (사용자·단말·설정·템플릿) |
| 로그 26GB/일, 1년 9.5TB | 단일 RDB 부적합 → **쓰기 최적화 저장소 + TTL/아카이빙** |
| 중복 탐지 캐시 2.6GB | Redis 단일 인스턴스로 수용 가능, **TTL 24h** |
| 피크 계수 2 | 큐가 **버퍼** 역할 수행 → 큐 적체 모니터링 필수 |

## 7. 트레이드오프 고려사항

```text
              무손실 (Durability)
                     ▲
                     │
                     │
   전달 지연 ◄───────┼───────► 중복 발송
   (Latency)         │        (Duplication)
                     │
                     ▼
              운영 비용 · 저장 비용
```

### 7.1 핵심 트레이드오프

| 선택 축 | A | B | 본 설계의 선택 |
| --- | --- | --- | --- |
| **전달 보장** | at-most-once (소실 허용) | **at-least-once** (중복 허용) | **B** — NFR-1이 소실을 금지 |
| **접수 응답 시점** | 큐 적재 후 즉시 202 | 로그 영속화 후 202 | **B** — 무손실 우선, 대신 P99 200ms로 제한 |
| **큐 구성** | 단일 큐 (단순) | **채널별 큐** (격리) | **B** — NFR-5 장애 격리 |
| **중복 탐지 위치** | 알림 서버 진입 시 | 작업 서버 전송 직전 | **양쪽** — 진입 시 요청 중복, 전송 직전 재시도 중복 |
| **재시도 정책** | 즉시 재시도 | **지수 백오프 + DLQ** | **B** — 제3자 과부하 회피 |
| **로그 보관** | 전량 장기 보관 | **30일 핫 + 아카이브** | **B** — 9.5TB/년 비용 |
| **템플릿 렌더링** | 작업 서버에서 | **알림 서버에서** | **A안 아님** — 렌더 결과를 로그에 남겨 재현성 확보 |
